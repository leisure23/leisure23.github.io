「这个算法是 O(n log n)，那个是 O(n²)，所以前者更快。」

这句话在学习的时候是对的，在工程里经常是错的。因为**大 O 描述的是增长趋势，不是实际耗时**。

## 先复习：大 O 到底在说什么

形式化地说，`f(n) = O(g(n))` 表示存在常数 `c` 和 `n₀`，使得当 `n > n₀` 时，`f(n) ≤ c · g(n)`。

翻译成人话：**当 n 足够大时，f 的增长不会比 g 快**。

注意两个关键词：**足够大** 和 **增长**。它们恰好是实践中最容易被忽略的两个点。

- 它是**上界**，所以 `3n` 是 `O(n)`，也是 `O(n²)`——两种说法都对，只是宽松程度不同。
- 它**丢掉了常数**，所以 `1000n` 和 `n` 都是 `O(n)`。
- 它**忽略小规模行为**，因为 `n₀` 之前的差距不算数。

## 第一个反例：常数因子能大到你怀疑人生

考虑两个求和的写法。

```cpp
// 版本 A:逐行遍历,一行 8 个 int,对缓存友好
long long sumByRow(const vector<vector<int>>& a) {
    long long s = 0;
    for (size_t i = 0; i < a.size(); i++)
        for (size_t j = 0; j < a[i].size(); j++)
            s += a[i][j];
    return s;
}

// 版本 B:逐列遍历,每一次都跳到另一块内存
long long sumByCol(const vector<vector<int>>& a) {
    long long s = 0;
    for (size_t j = 0; j < a[0].size(); j++)
        for (size_t i = 0; i < a.size(); i++)
            s += a[i][j];
    return s;
}
```

两个都是 `O(n²)`、都是两重循环、加法次数完全一样。但在 4096×4096 的矩阵上，行优先可能比列优先**快一到两个数量级**。

原因不在算法，而在 **CPU 缓存**：每次读内存都会把整条缓存行（通常 64 字节）搬进 L1。顺序访问能把这 64 字节全用上；按列跳着走，每个缓存行只用 4 字节，剩下 60 字节白搬了。

> 大 O 假设「每次内存访问代价相同」。这个假设在现代 CPU 上是假的，差距可能有 100 倍。

## 第二个反例：小 n 时，简单算法赢

假设有两个排序：

- 插入排序：`O(n²)`，但有极小常数，几乎是顺序扫描。
- 归并排序：`O(n log n)`，但有递归开销、额外数组分配。

它们的实际耗时大概是：

| n | 插入排序 | 归并排序 | 谁快 |
| --- | --- | --- | --- |
| 8 | ~64 次比较 | ~24 次比较 + 递归开销 | 插入 |
| 32 | ~1024 次比较 | ~160 次比较 + 递归开销 | 接近 |
| 1000 | ~10⁶ 次比较 | ~10⁴ 次比较 | 归并 |
| 10⁶ | 不可行 | ~2×10⁷ 次比较 | 归并 |

这正是**真实的标准库**在做的事：`std::sort` 是 introsort，小区间（一般 n < 16）直接切到插入排序。如果它老老实实「归并到底」，反而更慢。

所以正确的说法不是「O(n log n) 比 O(n²) 快」，而是：

> **当 n 足够大时，O(n log n) 的增长更慢。**

## 第三个反例：被忽略的空间与哈希

哈希表的平均查找是 `O(1)`，排序数组的二分是 `O(log n)`。看起来哈希完胜。

但：

- `O(1)` 的常数包含一次**哈希计算**和一次**随机内存访问**（大概率 cache miss）；
- 二分的 `log n` 每次都是**连续访问**，缓存命中率极高；n = 1000 时只比 10 次，几乎瞬间完成。

在数据量小、访问频繁的场景里，**排序数组 + 二分**经常赢过哈希表。这也是为什么有些高性能场景（比如某些路由表、某些数据库索引）宁可要二分。

## 怎么正确地比较两个算法

不要只问「复杂度是多少」，按这个顺序问：

1. **n 的实际范围是多少？** 如果 n 永远小于 100，常数决定一切。
2. **最坏情况出现的概率多大？** 快排最坏 `O(n²)`，但随机输入下几乎不会发生；而某些算法的「最坏情况」是攻击者可以刻意构造的（哈希碰撞攻击就是例子）。
3. **有没有隐藏的分配？** 每次 `push_back`、每次 `new`，都可能是一次系统调用级别的开销。
4. **内存访问模式如何？** 连续 > 跳跃，栈 > 堆。
5. **能不能实测？** 不要猜。写个 benchmark，跑几组真实数据。

复杂度分析的价值在于**排除掉不可行的方案**（比如 n = 10⁹ 时 O(n²) 直接出局），而不是在可行方案里选出最快的那个。后者只能靠测量。

## 一个常用的判断顺序

拿到问题时的思考顺序，我是这么排的：

- **先看数据规模**：n ≤ 10⁵ 时，`O(n²)` 是 10¹⁰，必挂；`O(n log n)` 是 1.7×10⁶，稳。
- **再看常数**：都是 `O(n log n)` 时，谁少一次内存分配谁赢。
- **最后看实际数据分布**：能提前剪枝、能缓存、能利用有序性，往往比换个算法更有效。

## 收尾

大 O 是个很好的**筛子**，但它不是**尺子**。

- 它回答「这个方案能不能撑住这个规模」；
- 它不回答「哪个更快」；
- 更不回答「哪个更值得写」。

把「O(n log n) 更快」这句话在心里改成「O(n log n) 增长更慢，在大 n 下更可能有优势」，你的判断会准确很多。
